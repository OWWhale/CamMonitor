
三个关键点：

1. **`CameraMonitorService destroyed` 之后还有 2 分钟的前置出帧日志** → 服务已销毁但释放流程没有走完，主线程卡住；采集线程独立于主线程所以仍在跑。
2. **只打印了 lens 0 的 `disposed`**，lens 2、lens 1 的释放日志一条都没有 → 卡在 lens 0 之后。
3. **没有崩溃栈**（`crash` buffer 干净）、没有 tombstone → 排除 SIGSEGV，是**卡死/ANR**，用户看到的就是"崩溃"。

#### 为什么会卡在 lens 0

调用链：

```
CameraMonitorService.onDestroy()
  └─ WebRtcManager.release()
       └─ MultiCameraCapturer.releaseAll()
            └─ sessions.forEach { releaseSession(it) }
                 ├─ capturer.stopCapture()      ← isCapturing 已被 retire 置 false → 早退
                 ├─ capturer.dispose()          ← 打印 "CameraXVideoCapturer disposed"
                 ├─ helper.dispose()            ← ★ 卡在这里
                 └─ track/videoSource.dispose()
```

`retireSessionKeepSlot()`（12:40:42 调用）已经对 lens 0 执行过 `capturer.stopCapture()` / `capturer.dispose()` / `helper.dispose()`，
**但没有把 `session.released` 置为 true**，于是 `releaseSession()` 认为它没释放过，**又完整释放了一遍**：

- `SurfaceTextureHelper.dispose()` 第二次调用会等待其内部 HandlerThread 退出，重复 dispose 直接卡住；
- 且 `releaseSession` 里的 `helper.dispose()` 是普通调用（非 runCatching），抛异常/阻塞都会把主线程带走。

**这是本次改动自己引入的坑**：看门狗和正常释放路径互不知情。

## 三、下一轮修复方案（按优先级）

### 修复 1：消除双重释放（P0，必做，改动小）

`MultiCameraCapturer.retireSessionKeepSlot()` 里释放完必须打上"已释放硬件"的标记，且 `releaseSession()` 要区分
"释放硬件" 与 "释放 track"：

- 给 `LensSession` 增加 `hardwareReleased: Boolean`；
- `retireSessionKeepSlot()` 末尾置 `hardwareReleased = true`；
- `releaseSession()` 里 `if (!session.hardwareReleased) { stopCapture/dispose/helper.dispose }`，track/videoSource 仍照常释放；
- 所有 `dispose()` 一律包 `runCatching`，并加超时保护（`SurfaceTextureHelper.dispose` 不允许在主线程裸调，改为后台线程 + join(timeout)）。

**验证**：退出观看后，日志应出现 `All lenses released`，且 `CameraX capture stopped cleanly` × N。

### 修复 2：解决后置零帧（P1，核心）

按下面顺序做**单变量验证**（每次只改一处，看 `frames delivered` 是否出现）：

1. **先只绑定后置单路**（`MAX_CONCURRENT_LENSES = 1`，强制优先后置）→ 确认后置单独能否出帧。
   - 若单独能出帧 → 问题是**并发数**，进入第 2 步；
   - 若单独也不出帧 → 问题在**后置镜头本身的绑定方式**（如 cameraId 0 是逻辑多摄，需要单独处理），与并发无关。
2. **并发降到 2 路，且优先后置**（打开顺序改成 `0 → 2 → 1`，或干脆只开 `0 + 2`）→ 看后置是否恢复。
3. 若"2 路后置 + 前置"仍不行，但"1 后置 + 1 前置"可以 → 说明本机只支持 **1 前 + 1 后**，此时应放弃"全部加载"，改为
   **后置多镜头按需串行切换**（切镜头时 `unbind` 旧 Preview + `bind` 新 Preview，画面会中断约 0.3~1s，但可用）。

参考依据：本机 MT6983（MTK），日志里出现
`E/CameraManagerGlobal: Camera 4 is not present. Ignore physical camera status change` ——
说明存在**逻辑多摄 + 物理子相机**结构，后置 `cameraId=0` 与 `cameraId=2` 很可能是同一逻辑设备的不同物理镜头，
同时打开会被 HAL 拒绝（绑定不报错，但不出流）。

### 修复 3：修 Surface 分辨率（P2）

`CameraXVideoCapturer.bindCameraSession()` 里：

```kotlin
val isLandscape = currentTargetRotation == ROTATION_90 || currentTargetRotation == ROTATION_270
val boundWidth  = if (isLandscape) maxOf(lastWidth, lastHeight) else minOf(lastWidth, lastHeight)
val boundHeight = if (isLandscape) minOf(lastWidth, lastHeight) else maxOf(lastWidth, lastHeight)
// → 竖屏得到 Size(720, 1280)
```

配合 `AspectRatioStrategy.RATIO_16_9_FALLBACK_AUTO_STRATEGY`（16:9 是**横向**语义），在竖屏下产生语义冲突，
CameraX 最终给出 192x108。三种候选改法（按推荐度）：

1. **绑定尺寸改用横向基准**：`Size(max(lastWidth,lastHeight), min(lastWidth,lastHeight))` 即 `1280x720`，
   让 `AspectRatioStrategy` 的 16:9 语义一致；
2. 去掉 `AspectRatioStrategy`，只用 `ResolutionStrategy(Size(1280,720), CLOSEST_LOWER_THEN_HIGHER)`；
3. 兜底：在 `SurfaceProvider` 收到 `request.resolution` 后做一次校验，若 `width < 640` 打印 ERROR 并
   改用 `FALLBACK_RULE_CLOSEST_HIGHER_THEN_LOWER` 重建（不推荐，太晚）。

**验证**：日志 `CameraX Surface requested:` 应变成 `1280x720`（或 `960x540`），观看端 `Remote frames delivered` 的尺寸同步变大。

### 修复 4：去掉启动时的夜间模式重绑（P3）

`WebRtcManager.startCameraCapture()` 在多路加载完成后立刻 `setNightModeSetting(...)`，而本机
`ExtensionMode.NIGHT` 不支持（`supported=false`）。改为：

- 加载阶段只把夜间模式作为**绑定参数**传进去（`preferNightMode`），不要在绑定后立即重绑；
- 或加判据：`isNightExtensionSupported == false` 时**跳过重绑**（因为 `configureLowLightFallback` 已经在首次绑定里应用了）。

**验证**：`Camera session bound` 每颗镜头只出现**一次**。

### 修复 5：看门狗策略放宽（P4 观感）

当前 10 秒零帧即退役，容易把"启动慢"误判成"无能力"。建议：

- 阈值 10s → **15s**，且只在**至少一路出帧**时才判定（现状已如此）；
- 退役后日志补一条人话说明：`Lens 1x retired: no frames in 15s (likely HAL concurrent-stream limit)`；
- 观看端对 `available=false` 的镜头除置灰外，长按/点按时弹一句"该镜头在当前并发下不可用"。
