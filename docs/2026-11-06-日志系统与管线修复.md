# 日志系统重构 + 管线修复（2026-11-06 13:13）

产物：`app/build/outputs/apk/debug/Camonitor-v1.0.7-20261106_131340-debug.apk`

本轮同时做了两件事：**日志系统 8 项优化**，以及上一轮诊断出的**相机/加密 4 项修复**。
所有改动只落在日志、相机管线、加密三处，未触碰已经跑通的信令与媒体链路。

---

## 一、日志系统：8 项

### 1.1 线程名（最大盲区）

`LogEntry` 新增 `thread` 字段，每行日志末尾带 `{线程名}`：

```
[2026-11-06 12:24:10.190 +1234.5s] [ERROR] [LensStream] {main} ...
```

上一轮判定「主线程卡住」只能靠 `stopCapture timed out waiting for the main thread`
这一条间接反推——日志本身看不出哪条记录在哪个线程。现在一眼可见。

### 1.2 会话边界 + 崩溃捕获

- `init()` 写 `===== SESSION START pid=... app=... api=... device=... =====`
- `markCleanShutdown()` 写 `=== SESSION END ===`，调用点：
  `CameraMonitorService.onDestroy`、`MainActivity.onDestroy`（仅 `isFinishing`，语言切换的
  recreate 不算）
- 启动时回读文件尾部 4096 字节，没有 END 标记就报 WARN
  `Previous session did not end normally ... killed by the system, force-stopped, or crashed`

此前「进程被杀」与「主线程卡死」在日志上都表现为「突然没有后续行」，无法区分。

- 新增 `UncaughtExceptionHandler`：崩溃时**同步**把栈写入同一个文件再退出。之前全项目
  没有这个 handler，崩溃栈只进 logcat，用户回头报告时早已滚掉。

### 1.3 容量：从 11 小时扩到数天

| | 旧 | 新 |
|---|---|---|
| 单文件 | 2 MB | 8 MB |
| 保留份数 | 4（含当前） | 6（含当前） |
| 总量 | 8 MB | 48 MB |

旧值在实测速率（11.5 KB/分钟）下只能存约 11.6 小时，**跨夜运行必然把前一晚覆盖掉**——
这正是「早上想回溯凌晨为什么连不上」却查不到的原因。

### 1.4 写入方式：从「每条开关文件」到「常驻缓冲」

旧实现每条日志 `PrintWriter(FileWriter(file, true)).use{}`，等于 open + write + close
三个 syscall，实测 92 次/分钟。现在：

- 一个 `BufferedWriter`（16 KB）常驻，攒够 **32 条**或空闲 **1 秒**才 flush
- 文件轮转在 flush 之后按 `file.length()` 判断（UTF-8 中文 3 字节，不能用字符数）
- 所有 writer 操作由 `Mutex` 串行化（`Dispatchers.IO` 是线程池，协程可能换线程）

### 1.5 队列有界

`Channel.UNLIMITED` → `Channel(4096)`。磁盘卡住时旧实现会无限堆积直到 OOM。
溢出不再静默：首次与每 1000 次打 WARN，另有 `droppedCount()` 可查。

### 1.6 级别开关

`AppLogger.minLevel`，默认 **DEBUG**（行为与旧版一致，不丢任何信息）。
日志页新增第三个图标（`Tune`）在 INFO / DEBUG 之间切换，开启时图标高亮。

会话关键行（SESSION START / END / 崩溃栈 / 级别变更本身）走 `mandatory = true`，
不受级别影响——否则把级别调到 INFO 会让 END 标记消失，下次启动误报「上次崩溃」。

### 1.7 导出：从单文件到全量 zip

`getLogFiles()` 返回当前文件 + 全部轮转副本；`exportBundle()` 打包成
`logs/export/cammonitor-logs.zip` 再分享（MIME 同步改为 `application/zip`）。

旧实现只发 `cammonitor.log`，**恰好丢掉轮转出去的那几小时**——正是报告想说明的部分。

> 导出前先 `flush` 缓冲，否则最新的几十行不会进包。zip 构建在 `Dispatchers.IO` 上，
> 不在主线程。

### 1.8 相对时间 + 格式化开销

- 时间戳后加进程内单调偏移：`[2026-11-06 12:24:10.190 +1234.5s]`。
  漫游触发 NTP 校正时墙钟会跳，相对时间不受影响。
- `SimpleDateFormat` 从「每行 new 一个」改为 `ThreadLocal` 复用（约 400 个调用点受益）。
- 空闲时不再每秒重发 500 条列表给 UI（原来即使日志页没打开也在持续分配）。

### 1.9 顺带合并的四处重复（占比 60%）

31 分钟样本里 2859 行，其中 1731 行是**同一件事记了四遍**：

| 位置 | 旧日志 | 处置 |
|---|---|---|
| `LanSignalingClient` | `Socket bound to peer` ×618 | 只在**真正新绑定**时打，并升为 INFO |
| `IncomingEnvelopeProcessor` | `Received verified message [IceCandidate]` ×616 | ICE 降为 DEBUG，其他消息仍 INFO |
| `CameraMonitorService` | `Received remote ICE candidate` ×327 | 删除（与下一条重复） |
| `WebRtcManager` | `Added remote ICE candidate` ×170 | 降为 DEBUG |
| `ViewerModeScreen` | `Received remote ICE candidate from camera` | 删除（观看端同上） |

补偿：`Selected ICE pair ... (remoteCandidates=N)` 现在是唯一需要看的一行，
同时带选中候选对和候选总数。

## 二、相机 / 加密：4 项

### 2.1 重建去重（12:44 三次互相拆台）

`startCameraCapture` 虽是 `@Synchronized`，但健康检查依据 `lensController.isRunning`，
而新建的 controller 要到**异步回调**才 RUNNING。中间的窗口里任何调用都判定「不健康」并把
前一次刚建好的管线拆掉——日志里那串 35ms 间隔的
`rebuilding (hadTrack=true) -> rebuilding (hadTrack=true)` 就是它。

新增 `beginCameraStart()/endCameraStart()` 闸门：

- 在途的重建请求被合并（只打一行 `coalescing this request`）
- 闸门在三个地方释放：异步回调（成功/失败都释放）、`stopCameraCapture`、同步异常
- 15 秒硬上限，防止回调永不到达把恢复路径永久锁死

同步半段抽成 `buildCameraPipeline()` 并包在 try/catch 里——否则 `createVideoSource`
之类的原生异常会让闸门卡满 15 秒。

### 2.2 Surface 授予看门狗

`startCapture()` 返回 true 只代表**会话绑定成功**，surface 是稍后由主线程上的
surface-provider 回调送来的。主线程被占住时回调永不执行 → 会话绑着、零帧、
`capture started` 日志却显示正常（这就是 12:24 那次 9.9 秒黑屏的机制）。

- `CameraXVideoCapturer` 新增 `surfaceGrantedAt` / `isSurfaceGranted` / `awaitSurface()`
- `LensStreamController.start()` 在 `openLens` 之后要求 **2.5 秒**内拿到 surface，
  否则 ERROR 并放弃这次启动（不再等 9 秒帧看门狗）
- `awaitFirstFrame` 失败时区分两种原因：
  - `surface was never granted (main thread blocked?)`
  - `surface was granted (sensor/HAL stall)`

### 2.3 sender 已销毁时跳过

`configureVideoSenders` 原来让异常逃出 `forEach`，一个 disposed sender 会导致**其余所有
sender 一起被放弃**，WARN 还写成 `Failed to configure video senders`（看不出是哪一个）。
现在内层单独捕获并降为 DEBUG，track 为 null 直接跳过。

### 2.4 ECDH 并发 Keystore 异常

`deriveEcdhKey` 每次 `KeyAgreement.getInstance("ECDH")`，而私钥来自 AndroidKeyStore——
它按 key 发一个不透明的 operation handle，**不可重入**。并发时第二个必然抛
`ProviderException: Keystore operation failed` / `Invalid operation handle`。

每轮重连稳定复现 9~11 次，每次都会让对应的信封解密失败 → 丢 ICE 候选。

现在：全局 `synchronized(ecdhLock)` + 失败重试 1 次（间隔 40 ms，仅失败路径）。
三个调用点（`IncomingEnvelopeProcessor`、`CameraMonitorService`、`ViewerModeScreen`）
都走同一把锁。

### 排查中发现并修掉的一个真回归

为消除 `Socket bound` 刷屏，最初把条件改成「仅在新建时绑定」：

```kotlin
if (current == null || current.isClosed) {
    peerSockets[senderId] = socket
    boundDeviceId = senderId   // ← 只在这里赋值
}
```

**`connectTo` 会在建连时预绑定 `peerSockets[recipientId] = socket`**（`LAN:490`），
因此出向连接的 reader 循环里 `current === socket` 成立，`boundDeviceId` 永远是 null。
后果：EOF 时 `boundDeviceId?.let { peerSockets.remove(id) }` 不执行 → 死 socket 永久留在
路由表 → 之后每次发送都复用它 → **正是「多次重连后无响应」的症状**。

已改为「日志只在新建时打，`boundDeviceId` 无条件赋值」：

```kotlin
if (current !== socket && (current == null || current.isClosed)) {
    peerSockets[senderId] = socket
    AppLogger.i(TAG, "Socket bound to peer $senderId (inbound=$learnedViaAccept)")
}
boundDeviceId = senderId   // finally 清理依赖它，不能省
```

## 四、行为变化须知

1. **默认日志级别仍是 DEBUG**，所以写入内容与旧版基本一致（除了被合并的重复行）。
   只有手动切到 INFO 才会减少落盘量。
2. **以下 grep 断言已失效**，请改用新写法：

   | 旧 | 新 |
   |---|---|
   | `Received remote ICE candidate` | 已删除，看 `Selected ICE pair ... (remoteCandidates=N)` |
   | `Received verified message [IceCandidate]` | `Received [IceCandidate]`（DEBUG） |
   | `Added remote ICE candidate` | 同名（DEBUG） |
   | `Socket bound to peer`（每包一条） | 同名（INFO，每次新建连接一条） |

3. **日志格式变了**：时间戳后多了 `+1234.5s`，tag 后多了 `{线程名}`。
   正则按 `^\[.*\] \[INFO\] \[Tag\]` 匹配的脚本仍然可用。
