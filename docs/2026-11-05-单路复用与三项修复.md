# 单路复用重构 + 三项修复（2026-11-05 夜）

目标：把「多镜头并发上传」改成「单路传感器复用」，并修掉切换卡死 / 重连无响应。

## 1. 架构改动：多路并发 → 单路复用

| 项 | 改前 | 改后 |
|---|---|---|
| 物理镜头 | 一次开 3~4 颗，各自一条 VideoTrack | **同一时刻只开 1 颗** |
| m-line | 每颗镜头一条，mid 需按连接映射 | **恒定 1 条**，mid 永不变化 |
| 切换 | 观看端换 sink（本地） | 镜头端关旧传感器 → 开新传感器，复用同一 VideoSource/Track |
| 协商 | 需要 m-line 顺序保证 | **切换不重新协商、不重连** |
| 编码预算 | 按路数分摊（每路 ≤450kbps） | 单路独占 2.5 Mbps |

新增 `data/camera/LensStreamController.kt`，删除 `MultiCameraCapturer.kt`。

失效根因回顾：CameraX 只保证每台设备 ≤2 个并发 UseCase，且 MTK/高通 BSP 常拒绝第三颗物理相机 —— 所以「3 路并发」在规范层就不成立，表现为「track LIVE 但画面全黑」。单路后该约束消失。

线程模型：

- 所有相机操作在单线程 `LensStream-ops` 上串行（开/切/恢复不会交叉）。
- `stop()` 例外：在调用线程（通常是主线程）**同步** `stopCapture()` 切断帧流，再把 `dispose()` 排进 ops 队列；这样上层可以立刻销毁 VideoSource，不会出现「往已销毁的 source 里推帧」。

## 2. 修复一：切换结果回传（卡灰）

协议新增 `ControlCommand.LensSwitchResult(lensId, status, activeLensId, message)`，`status ∈ {OK, ALREADY_ACTIVE, BUSY, FAILED}`。

镜头端 `LensStreamController.switchTo()` 对**每一个**请求恰好回一次结果，包括以前静默 return 的几种情况：

- 目标 == 当前镜头且仍在出帧 → `ALREADY_ACTIVE`
- 目标 == 当前镜头但**已停止出帧** → 强制重开（顺带当成「点一下刷新」）
- 有切换正在进行 → `BUSY`
- 打开失败 / 4s 内无首帧 → 自动回滚到上一颗，回 `FAILED`

观看端：

- 点击后进入 pending（镜头条显示转圈，其余按钮禁用）
- 收到 `LensSwitchResult` 或「能解释这次点击的 `LensListReport`」→ 清除 pending
- 6s 无应答 → 清 pending + 提示「镜头切换超时」（比镜头端 4s 首帧预算长，避免误报）

## 3. 修复二：重连无响应

| 症状 | 改动 |
|---|---|
| 状态标记活着但管线已死，重连直接 return | `startCameraCapture()` 前置**真实健康检查**（controller 是否 RUNNING），不健康就整条重建 |
| `synchronized releaseCameraHardwareOnly()` 持锁等 2s | 释放流程改为「同步停帧 + 异步销毁」，不再持锁阻塞 |
| 每次切换 `new Thread("CaptureThread-dispose")` 泄漏 | 统一走单线程 ops，每个 capturer 只 dispose 一次（`disposed` CAS 保护） |
| 快速重连时旧 capturer 仍在推帧 | 先 `stopCapture()`（会 `stopListening` + unbind preview）再销毁 source |
| 夜视/光照延迟 Runnable 在 stop 后重新 bind | `bindCameraSession()` 增加 `isCapturing` 守卫 |
| 绑定成功但 9s 无帧（黑屏） | 健康看门狗检测帧计数停滞 → 自动重开当前镜头 |

**未使用 `unbindAll()`**：只 `unbind(自己的 preview)`。单路下这是唯一正确的解绑粒度。

## 4. 修复三：加密开关

不做。WebRTC 媒体强制 DTLS-SRTP，ECDH/AES-GCM 只作用于信令小报文，关掉不会提升画质。画质的真实杠杆是分辨率 / 码率 / 帧率。

## 5. 复查补漏（第二轮，22:02）

首版打包后按「协议往返 / 单路残留 / 生命周期 / 跨版本兼容」重查一遍，又修了 5 处：

| 问题 | 后果 | 修法 |
|---|---|---|
| 重建管线后新建了 VideoTrack，但已存在的 PeerConnection 仍握着旧 track（已 dispose） | 相机重启后所有观看端永久黑屏，且相机是 answerer 无法自己重协商 | 重建后 `sender.setTrack(newTrack, false)` 换轨（不改 SDP，无需协商）；无 sender 时才 addTrack 并告警 |
| `onCameraLost` 无条件触发 → 服务 1s 后重建 → 又失败 → 每秒重启 | 相机被占用时发热/耗电，且永不恢复 | 服务端指数退避（1/2/4/8/16s，上限 20s），连续 5 次放弃；新 Offer / 唤醒时重置计数 |
| 切换失败且「上一颗 == 目标镜头」时无回滚对象，state 直接 IDLE | 画面黑掉，且没有任何恢复通路（看门狗只盯 RUNNING） | 该分支主动回调 `onCameraLost` → 走退避重建 |
| 启动时一颗都开不出来只置 flag，不通知 | 相机永久死掉直到进程重启 | 启动失败也回调 `onCameraUnexpectedClosed` |
| 切到前置时手电筒"成功"但根本没闪光灯 | UI 显示已开、实际不亮 | 记录朝向，前置时打警告（状态保留，切回后摄时生效） |

同时确认过的点（无需改）：

- `LensSwitchResult` 旧版 App 解析为 null → 静默忽略，不崩。
- 观看端声明 4 条 RECV_ONLY video m-line、镜头端只填 1 条 → answer 里其余为 inactive，SDP 合法（此前 3 填满 4 已验证过同路径）。
- 切换期间 `healthCheck` 被 `switching` 挡住，不会和 `doSwitch` 抢相机。
- 切换后新 capturer 重新取设备旋转、重新算 FPS 区间、重新广播 `FpsReport`。
- 观看端 `_activeLensId` 以镜头端 `LensListReport.activeLensId` 为准，不再依赖 mid 映射。
- 快速重连：新 Offer 时 `startCameraCapture` 走真实健康检查，健康则复用，不健康整条重建并用新 track 换轨。

**部署注意：两端必须同版本。** 旧观看端的切换逻辑是「本地 selectRemoteLens 成功才发命令」，单路相机没有多 track，它永远不会发切换请求；新观看端配旧相机仍可用（靠 `LensListReport` 兜底）。

## 6. 验证清单（真机）

1. 两端安装同一包；镜头端 `.114` 起流，观看端 `.113` 连上 → 应出画面（默认主摄）。

## 8. 第三轮：画质 / 常亮 / 滑动解锁（22:36）

### 8.1 画质骤降的真因：分辨率请求写错了坐标系

`bindCameraSession()` 原来按屏幕方向交换宽高，竖屏时把 `Size(720,1280)` 交给 CameraX。
CameraX 的 Size 是 **sensor 坐标系（恒为横向）**，竖版 target 在 16:9 候选集里匹配不到，
`CLOSEST_LOWER_THEN_HIGHER` 退化到 `640x360` 甚至 `192x108`，再被
`VideoSource.adaptOutputFormat(1280,720)` 放大 —— 全程日志都写"720p"，画面却是糊的。

改为只做归一化（`width = max(w,h)`，`height = min(w,h)`），不再按旋转交换；屏幕方向仍由
`targetRotation` 的旋转元数据表达。日志改为 `CameraX Surface granted: WxH (requested=1280x720)`。

> 注意：竖屏时 granted 打出 `720x1280` 是正常的（同一路 stream 的旋转呈现），
> 要看的是**面积**是否从 192x108 级别回到 1280x720 级别。

### 8.2 屏幕常亮（防休眠主力）

`CameraModeScreen` 增加 `FLAG_KEEP_SCREEN_ON`（进入加、退出清）。这是应用侧唯一能阻止
系统进 Doze 的手段，也就堵住了「凌晨熄屏 → 进程被冻结 → 连不上」的链路。
AMOLED 上全黑窗口 + 1% 亮度几乎不耗电，代价可接受。

保留原有 `PARTIAL_WAKE_LOCK` + `WifiLock`；`PARTIAL_WAKE_LOCK` 的 `acquire(24h)` 到期问题
仍未处理（列为待定项）。

### 8.3 黑屏 = 锁定，滑动解锁

- 点击「黑屏」按钮与 60s 无操作走**同一个** `enterLocked()`，没有"黑屏但不锁"的中间态。
- 锁定期间：全屏纯黑、隐藏 HUD、`pointerInput` 接管手势。
- 轻点只浮现 1.5s 的极暗提示（`#2A2A2A` 滑块 + `#3A3A3A` 文案），随后淡出 —— 常驻会在 AMOLED 上留残影。
- 滑动距离 ≥ 屏宽 30%（下限 120px）且距上锁 ≥ 300ms 才解锁，避免"点按钮那一下"和双击误开。
- 解锁后 3s 冷却，窗口重新获得焦点时重新藏系统栏（挡不住通知栏下拉，但能收回系统栏）。
- 锁定时返回键被吞掉，不会退出镜头模式。
- `isLocked` 改用 `rememberSaveable`：Activity 重建（语言切换会 recreate）不再突然亮屏。
- 锁定时强制关闭重命名对话框（对话框是独立 window，会浮在黑屏上并可用外部点击关掉，等于绕过锁）。
- 对话框打开期间暂停 60s 计时，避免输入时被锁。
- 锁定状态下即使进入 `PAUSED_INACTIVITY` 也保持黑屏（要看到待机卡片需先滑动解锁）。

## 9. 第四轮：镜头端降耗（22:52）

实测 `.114` 发热明显，AIDA64 只暴露电池温度一个传感器（无热区数据），因此**不做热保护**，
只做可量化的功耗削减。日志按要求保留（跨网段调试还需要）。

| 项 | 改动 | 为什么 |
|---|---|---|
| 采集帧率封顶 | `finalFps = selected.upper.coerceAtMost(lastFramerate)`，并把 AE 区间裁成 `[lower, min(upper, target)]` | 目标 20fps 时最接近的区间常是 `[15,30]`，原代码直接取 upper=30，传感器按 30fps 出帧、编码器再丢掉一半 —— 白付 ISP + 编码功耗 |
| 无人观看停流 | `60s → 15s`（`NO_VIEWER_PAUSE_MS`），三语文案同步 | 相机+编码是最热的东西，没人看还空转一分钟没有收益；重连有 `CameraWaking`，1~2s 就能开回来 |
| 夜视触发阈值 | 进入 `10 → 5 lx`，退出 `25 → 15 lx`；单测常量同步 | NIGHT 扩展是多帧合成，是夜间最大热源。10 lx 会把整晚的昏暗房间都判成夜景 |
| 屏幕亮度 | 解锁态系统亮度 → `0.55` | 屏幕是前三热源；监控设备不需要 100% 面板 |

未做：

- **日志优化**：按要求保留（每条 open/write/close 文件确实费电，但跨网段调试需要）。
- **热保护**：无可用温度传感器。
- **本地预览节流**：本地预览是 GPU 合成，收益约 0.2W，但降帧后观感明显变差，不划算。
- **WifiLock 降档**：跨网段场景优先保证链路稳定，不动。

验证点：

- 日志 `Selected hardware AE FPS range: [15, 30] -> [15, 20], finalFps=20`。
- 观看端 FPS 徽标应显示 20。
- 断开观看端 15s 后进入 PAUSED_INACTIVITY。
- 夜间（10~15 lx 的昏暗房间）不再进入 NIGHT 扩展：日志里没有 `Binding CameraX with ExtensionMode.NIGHT`。
